# 🤝 Contributing Guide (협업 가이드)

우리 팀(고준석, 채민성, 박영세)의 일관되고 안전한 Git 협업 및 코드 품질 유지를 위한 가이드라인입니다. 모든 팀원은 본 가이드의 규칙을 준수하여 작업합니다.

---

## 1. 브랜치 전략 (GitHub Flow)

우리 팀은 빠른 피드백 주기와 명확한 브랜치 생명주기를 위해 **GitHub Flow**를 적용합니다.

### 💡 GitHub Flow 채택 이유 (3줄 요약)
1. 복잡한 릴리즈 브랜치 없이 `main`과 `feature` 브랜치만으로 직관적이고 가벼운 워크플로우를 유지할 수 있습니다.
2. 모든 작업을 PR(Pull Request)로 공유하고, 코드 리뷰와 로컬 테스트로 병합 전 품질을 확인합니다. 현재 저장소에는 GitHub Actions 워크플로가 없습니다.
3. `main` 브랜치를 항상 배포 가능한 안정 상태로 유지함으로써 팀 전체의 병합 충돌과 협업 병목을 최소화합니다.

### 브랜치 구성 원칙
- `main` : 항상 배포 가능하고 테스트를 통과한 깨끗한 상태 (직접 push 금지, PR 병합 필수)
- `feature/*` : 새로운 기능 개발 또는 유틸 함수 단위 브랜치
- `refactor/*` : 코드 구조 개선 및 패키지 재배치 브랜치
- `fix/*` : 버그 및 경로 수정 브랜치

---

## 2. 브랜치 네이밍 규칙

브랜치 이름은 작업 목적과 작업자를 명확히 식별할 수 있도록 아래 규칙을 엄격히 준수합니다.

`형식: <type>/<member_name>-<feature-name>`

### 팀 공식 브랜치 명명 예시:
- `feature/ko-math-utils` (팀원 고준석: 수학 유틸리티 개발)
- `feature/chae-string-utils` (팀원 채민성: 문자열 유틸리티 개발)
- `feature/park-date-utils` (팀원 박영세: 날짜 유틸리티 개발)
- `refactor/ko-package-structure` (팀원 고준석: 패키지 디렉터리 레이아웃 리팩토링)
- `feature/chae-advanced-strings` (팀원 채민성: 고급 문자열 처리 함수 개발)
- `feature/park-test-suite` (팀원 박영세: 종합 단위 테스트 스위트 개발)

## 3. 커밋 메시지 컨벤션

커밋 메시지는 변경 사항의 목적과 범위를 명확히 전달해야 하며, 원자적(Atomic) 커밋을 원칙으로 합니다.

### 기본 형식
`type: subject`

### Type 태그 정의
- `feat:` 새로운 기능 함수 추가
- `fix:` 버그, 예외 처리, 경로 오류 수정
- `docs:` 문서 작성 및 수정 (README, docs 하위 가이드 등)
- `refactor:` 코드 리팩토링 (기능 변경 없는 구조 재배치)
- `test:` 단위 테스트 코드 추가 및 수정
- `chore:` 빌드, 설정, 패키지 파일 유지보수

메시지는 `type: subject` 형식으로 작성하며, subject는 한국어로 변경 대상과 목적을 설명합니다.

### ⚠️ 금지되는 무의미한 커밋 메시지 (반려 대상)
아래와 같이 변경 대상이나 목적이 모호한 커밋 메시지는 엄격히 금지됩니다:
- 대상 불명 단어 단독 사용: `update`, `fix`, `temp`, `wip`, `final`, `test`
- 무엇을 왜 바꿨는지 드러나지 않는 경우: `bug fix`, `edit file`, `modify code`

## 4. PR (Pull Request) 작성 규칙

모든 작업은 PR을 통해 `main` 브랜치로 병합됩니다.

1. **이슈 연동 필수**: PR 본문에 반드시 `Closes #<이슈번호>` (또는 `Fixes #<이슈번호>`)를 명시하여 작업 추적성을 확보합니다.
2. **필수 기재 항목 (What / Why / How)**:
   - [PR 템플릿](../.github/pull_request_template.md)의 연결 이슈 및 What / Why / How 구조를 사용합니다.
   - **변경 사항 (What):** 어떤 기능/파일이 수정되었는지 상세 목록 작성
   - **변경 이유 (Why):** 이 변경이 왜 필요하며 어떤 요구사항을 충족하는지 서술
   - **테스트 및 검증 (How):** `pytest` 실행 결과, 엣지 케이스 확인 여부 명시
3. **병합 요건**:
   - 최소 1명 이상의 팀원 승인(Approve) 필수
   - 단위 테스트(`python -m pytest`) 전원 통과 확인
   - 미해결 코멘트(Unresolved Conversations)가 없을 것

테스트 통과와 미해결 코멘트 해소는 팀 운영 기준입니다. GitHub의 필수 상태 검사나 대화 해결 강제 설정과 구분하며, 확인한 브랜치 보호 설정은 [제출 인덱스](../SUBMISSION.md#5-브랜치-보호-규칙-증빙)를 참고합니다.

---

## 5. 코드 리뷰 최소 품질 기준

단순한 승인이 아닌, 실질적인 코드 품질 향상과 지식 공유를 위해 리뷰합니다.

1. **"LGTM / 확인했습니다" 단독 작성 금지**:
   - 반드시 특정 코드 라인(Line-by-line)을 지정하여 실질 질문, 대안 제시, 리스크 지적 코멘트를 작성합니다.
   - 예시: 0으로 나누기 방어 코드 제안, 탭/줄바꿈 공백 문자 처리 정규식 제안, 타입 힌트 누락 지적 등
2. **상호작용 및 피드백 반영 기록 필수**:
   - PR 작성자는 리뷰어의 코멘트에 답글을 달고, 추가 커밋을 통해 피드백을 반영한 증빙을 남깁니다.

## 6. 충돌 (Conflict) 대응 흐름

병합 중 충돌이 발생할 경우 다음 절차를 따릅니다.

1. **상황 공유**: 디스코드/슬랙 및 PR 코멘트를 통해 충돌 대상 팀원에게 발생 파일과 상황을 즉시 공유합니다.
2. **로컬 해결 절차**:
   ```bash
   git checkout feature/내브랜치
   git fetch origin
   git merge origin/main
   # 충돌 마커(<<<<<<<, =======, >>>>>>>)를 확인하고 수동 편집
   git add <충돌_해결_파일>
   # 저장소 루트에서 해결 후 기존 기능 검증
   python -m pytest tests/ -q
   git commit -m "fix: main 병합 충돌 해결"
   git push origin feature/내브랜치
   ```
3. **문서화**: 충돌 해결 즉시 `docs/conflict-resolution.md`에 충돌 유형(Hunk/비자명), 충돌 마커 원본, 해결 전략(Keep Both / Rename Migration 등), 배운 점을 상세히 기록합니다.

원본 마커·터미널 로그·화면 캡처가 없으면 설명용 예시와 실제 기록을 명확히 구분합니다. 과거 커밋의 파일 경로를 현재 경로로 바꾸어 수행 증빙처럼 작성하지 않습니다.

## 7. 개발 환경 및 문서 갱신

- 저장소 루트에서 [가상환경·pytest 가이드](command/python_venv_pytest.md)를 따라 테스트합니다. 현재 공개 함수는 `src/utils/`, 테스트는 `tests/`에 있습니다.
- 이슈·PR 생성은 [이슈 명령어](command/gh_issue_create.md)와 [PR 명령어](command/gh_pr_create.md)를 참고합니다.
- API나 경로가 바뀌면 [README](../README.md)를 갱신하고, 협업 증빙이 추가되면 [제출 인덱스](../SUBMISSION.md)도 갱신합니다.
- `utils/string-policy.md`는 정책 문서입니다. 정책 변경 시 `src/utils/string_ops.py`의 실제 동작과 테스트가 일치하는지 별도로 확인합니다. 현재 함수는 스페이스만 제거하며, 탭·줄바꿈 제거는 후속 구현이 필요합니다.
